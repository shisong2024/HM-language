## DN-001：语言方向与文档治理

**状态：用户已提出并确认维护需求；2026-10-12 建立文档。**

初衷：语言已经包含多个相互作用的机制，单凭设计者当时的喜好会使语义漂移，旧施工文档也容易与当前版本冲突。

目的：让使用者知道实际行为，让设计者能够解释每项功能解决了什么问题、为何付出这些代价。保留实验自由，但不把实验自动纳入主语言。

方向：以 HM 为核心，通过 ADT、字典 elaboration、效果传播和适量语法糖组合表达能力。评估需求频率、实验价值、推断可预测性、模块一致性与维护成本，不以复制某个成熟语言为目标。

维护决策：语言参考写事实；本文件写理由与决策；TODO 写下一步及验收；archive 保存当时的实现证据与被替代计划。今后每次实质设计讨论按此维护。

## DN-002：隐式参数、精确字典与类型变量共享

**状态：先前用户确认；R1/R5 标志已在主源码；本轮仅核对源码。**

初衷：默认实现提高调用便利，但调用者仍要能明确选择反序等不同语义；原来同名注解变量分别刷新，无法正确描述容器字典工厂。

目的：保留显式字典控制，让类型需求自动传播；用单向候选匹配实现 Ord [a] 等工厂，不让搜索反向决定普通函数的参数类型。

已确认规则：精确 `@{o=...}`；移除 LetImp 路线；同一 def 的隐式参数与 body 注解共享同名类型变量，不同 def 独立，let RHS 注解局部独立。重叠同层报歧义，不采用更具体优先；搜索有循环和深度保护。

代价：具名的具体约束也可能保留到调用者；两个实例化带出同名不同类型槽位时，默认搜索能分别填充，显式按名字覆盖可能不唯一。多个 Ord Int 可以表达不同策略，所以当前不保证“任何上下文都只有一个全局实现”。

2026-10-12 核对：主源码已包含 prepareDecl 与递归 resolveWanted；当前 Prelude 也有 Ord/Show 容器实例。R5 历史 351/0 仍是副本结果；当前主测试接口与 Prelude API 迁移需要另外验收。

验收：泛型函数不被默认 Int 实例特化；显式覆盖准确；递归实例可用；缺子字典指向真实类型；同层重叠、循环与增长目标有可定位诊断。

## DN-003：能力接口与普通 data 是否区分

**状态：用户授权基础版实施；隔离验证；主源码尚未采用。**

初衷：Person 描述数据形状，Ord/Show 描述如何操作数据；全部写成 data 虽然实现统一，用户理解上缺少角色区分。

目的：使接口依赖可见，限定默认搜索空间，提供更准确的错误，减少无意把任意数据注册为隐式候选的情况。

推荐草案：新增 `ability` 一类名义声明，底层仍使用 Record/字典传递。字典保持一等值，普通 def 可以保存/构造，implicit def 才注册；隐式参数和候选限制到声明为能力的类型。

下面只是讨论语法，当前 Parser 不支持：

```text
ability Show a { show :: a -> String };
ability Ord a { cmp :: a -> a -> Ordering };
```

理由：声明角色与类型推断结构可以分开；需要的是候选资格和依赖含义，不必同时引入接口继承、HKT、关联类型或唯一实例规则。

代价：`{config :: Config}` 等普通上下文依赖将被禁止，需要显式参数或能力封装；现有程序有兼容性迁移成本。限制候选类型并不解决重叠、字典依赖循环或模块一致性。

能力可保存配置等普通字段，不仅限于函数。能力值依然可以显式传递、存储和返回；未注册的字典不参加默认搜索。能力字典与静态 effect 标签分开，声明能力不自动创建同名效果。

初次讨论的待决清单（下方追加记录基础版取舍，剩余扩展另行确认）：

- 是否硬性禁止所有普通数据隐式参数，还是只增加接口声明而保留通用上下文参数？
- 关键字采用 ability、trait、interface 还是其它名称？
- 字典构造语法是否沿用单构造器 Record？是否允许模式拆解？
- 方法是否自动生成全局包装函数？若生成，如何避免 Show.show 等同名方法碰撞？第一版建议继续显式包装。
- 类型别名展开后如何判定能力资格，普通 data 包装能力是否仍算能力？

验收：普通 data 与能力误用报清楚错误；已有 Show/Ord 实例能迁移；显式反序字典可用；能力工厂仍遵守 R5 终止与效果规则；方法保存带效果函数时 R4 传播正确。

初次讨论沿革：当时助手推荐能力专用声明，尚未获得实施确认；后续授权与验证记录如下。主源码未采用时不写入 Language Reference 的现有特性。

2026-10-12 追加：用户授权先给最基础 ability/effect 代码，明确排除 State Int 等参数化效果。基础版采用 ability keyword、单 Record/空标记构造器、普通字典值、仅能力可隐式使用与固定效果标签声明。简写 `ability A {...};` 和显式构造器形式均支持；方法不自动全局导出，普通配置转显式参数或能力包装。

交付见 [35](../TODO/35-Ability与固定Effect基础原理与完整代码.md)：隔离副本严格编译，332/0（新增 50），26 文件用例、模块/REPL/reload 和金标通过。主源码未改，当前语言参考不提升采用状态。兼容变化和既有库/事务边界在 35 单独说明。

## DN-004：同名字段与字段多态

**状态：备忘录方案与助手建议；未实现。**

初衷：Person.name、Cat.name 等自然字段名称因全局 FieldTab 限制而冲突；人为添加前缀损害可读性。

目的分两步：先允许多个具名 Record 使用同名字段；在真实使用证明需求后，再支持泛型 `def getName x = x.name`。

第一阶段建议保留 FieldGet/FieldUpdate 等节点，到类型检查阶段按接收者类型选字段，最后转为现有 getter/Match。修改涉及构造、更新、模式、Qualify、Pretty、字段可见性与重载，不只是改 Map 的值类型。

必须在普通约束传播后再判断不确定访问，不能因为遍历到 x.name 时暂时不知道 x 类型就立刻拒绝；后面的普通调用可能确定 x 为 Person。不得在多个字段候选间随意猜类型。

兼容性待决：现有唯一字段名会在去糖后帮助推断接收者类型。若新阶段一律要求事先知道接收者类型，旧 `def age x = x.personAge` 也可能失效。建议保留唯一可见字段的现有推断行为，多候选时等待普通类型信息；此规则尚需确认。

第二阶段可增加专用 HasField(label, record, result) 约束，保证 label+record 唯一决定 result。复用 wanted/elaboration 传递 getter，真实字段证据由编译器提供，不允许普通 implicit 任意覆盖。

手写 HasName 是当前机制可做的实验，getter 先用构造器模式匹配，避免与字段改造绑定。它用于验证表达需求，不自动决定 x.name 的语义。

不推荐现在批量生成 HasName/HasAge 类型：需要管理生成名字、重复声明、字段类型、实例重叠、导入与可见性。显式 deriving 是后续备选，`get (*)`/ignore 的未来定义与模块作用域规则暂时不设计。

标签待决：若希望一个 getName 跨模块访问同名真实字段，就不能给每个字段声明互不相等的标签。倾向同名公开字段共用内部标签，记录类型身份负责区分接收者；可见性和模块限定规则需明确，内部标签不必变成用户 data。

还要决定多构造器 ADT 的部分字段：结果类型唯一不保证读取成功。第一轮优先单构造器 Record；现有部分字段访问行为另行处理，不假装已经总化。

暂不加入虚拟字段、字段别名映射、完整 Lens、开放 Record row。验收重点是消歧与推断顺序无关、更新准确、模块间标签/类型身份一致，以及旧程序兼容边界清楚。

## DN-005：Tuple 实例与 Show 的含义

**状态：当前机制已知；脚本生成是建议，未排入实现。**

初衷：手写每个元数的 Ord/Show 重复，但 TTuple [T'] 的元素类型序列不能由一个普通 HM 变量表示。

目的：减少样板，同时保留明确的字典实现与自定义语义。

建议近期按元数提供实例，可脚本生成常用元数。保留当前 Tuple 表示。编译器内自动合成可作为未来显式派生原型，不分别硬编码 Ord/Show 的全部容器规则。

代价：脚本生成仅覆盖有限元数；二元嵌套能组合，但不等于扁平三元组。若用户需求集中在大元数组合，需重新评估数据建模而非立即增加 variadic generics。

命名讨论：助手建议用 show 表达供人阅读的表示。当前用户 Prelude 实际采用 show 入口和 show' 字段，showStr=id；不能把“建议带引号/可解析”写成规范。展示是否要转义、是否要求与 read 往返、面向用户还是调试，应按实际库需求另行决定。

验收：二元/三元和嵌套组合，异构元素的子字典正确，缺实例与重叠诊断清楚；生成文件可以复现且不用修改类型系统。

## DN-006：HKT、higher-rank 与替代路线

**状态：学习与远期实验；建议推迟。**

初衷：想统一 mapList/mapMaybe 等容器操作，讨论过 Functor、Type Witness/Apply、GAT 与参数化模块。

目的：识别真正需要的新表达能力，避免以隐式参数掩盖类型级结构缺口。

当前不能写 f a；受限 HKT 仍需要 kind、类型应用、替换、合一、解析与泛化规则。字典中保存 `forall a b. ...` 的多态方法是另一个问题，增加 HKT 不自动提供 higher-rank 字段。

可以考虑按每次操作实例化的多参数字典，但它不等于一个含全称多态方法的 Functor f 值，而且可能增加结果类型决定关系和歧义。不能据此宣称已绕过全部 HKT/rank 问题。

Type Witness/Apply 仍需类型归约；GAT 仍需投影与归约；参数化模块仍需抽象类型构造器的模块类型规则。它们都不是普通 ADT 免费提供的功能。

推荐继续普通高阶函数与容器专用 map。只有多个真实程序反复需要抽象类型构造器，才比较独立原型成本。Type Witness/Apply 从“近期值得做”调整为学习候选，无当前用户需求就不排期。

## DN-007：效果跟踪与能力依赖

**状态：自动传播由用户先前确认；主源码已有 R4；仍有求解边界。**

初衷：调用 Console 操作的函数应自动带标签，并沿调用链和高阶回调传播；无需人为为每个函数重复写效果。

目的：静态检查允许的效果上界，支持类型查询且不产生真实输出，区分闭包构造与调用。

标签表示可能效果；箭头是潜在效果，表达式有立即效果；分支保守合并。纯箭头不能接受 Console 操作。空标签不证明终止、无异常或计算便宜。

能力字典提供操作实现，effect 描述执行的行为。自动字典构造应纯，字典方法可带效果。只有标签集合而没有实际原语/操作规则，不会生成新的运行能力。

建议优先验证变量实例化、约束替换、逆变位置、失败回滚、递归终止与字典构造效果。FileIO/State/Exception 随实际操作进入语言；语言级可恢复 Exception 与解释器当前报错不是一回事。

自定义标签与 algebraic effects/handlers 分开。后者需要控制流捕获与恢复，作为独立研究线，当前推迟。

验收：纯、直接 Console、链式、高阶、分支、递归、拒绝纯上界、候选构造纯度，以及类型检查失败之后状态不污染。

### 2026-10-12 追加：用户优先推进 ability/effect

用户明确希望近期以完善 ability/effect 为主线，并要求先设想完整效果系统。这确认了工作重点，没有确认全部新语法或 handler 方案。

本轮初衷：把现有标签传播完善为可组织真实程序的规则，解释能力实现、静态行为上界与执行边界怎样协作。目的：类型可检查、实现可提供、执行时机明确，不能靠“增加标签”代替实际能力。

完整设想见 [34](../TODO/34-完整Effect与Ability协作设想.md)：值类型/立即与 latent 效果、集合变量与约束、标签身份及参数、方法上界和实现替换、入口提供、执行与泛化，以及 Throw/State 和通用 handler 的不同成本。

关键判断：提供字典不自动消除方法效果；FileIO 实现不能借 Console 接口隐藏行为；纯不保证终止或无运行期失败。随 mock 获得更精确效果需要方法效果参数或真正处理机制。引入 State 后须处理可变值泛化与资源逃逸。

## DN-008：顺序块、guard 与模式函数

**状态：建议和待设计事项；当前均未支持。**

初衷：嵌套 let/if/match 影响实际带效果程序和分类逻辑的可读性。

目的：提供清楚的绑定范围与执行顺序，尽量用现有表达式表达，不借用 Monad 或增加计算上下文。

顺序块草案：`do { x = f a; g x; h x }`。建议最后一项是返回值表达式，前项从左到右执行，绑定只对后续可见；空块、末尾只有绑定、尾随分号和遮蔽规则尚待决定。暂不使用暗示特殊 bind 的 `<-`。

**本轮校正先前建议：不能直接承诺脱糖成 let _ 总会执行前项。** 当前带隐式约束的 let 会 generalize 为字典函数，未使用绑定就不执行 body。`let u=putStrLn(show 1) in 2` 是需要覆盖的边界。

可比较专门 Seq 表达式，或让顺序语句的 wanted 在外层解析后再求值。绑定的多态泛化与“必须执行初始化”要单独定规则；用 lambda 应用强制求值又可能失去 let 多态。这些都需要实际类型/效果设计，不能只改 Parser。

Guard 建议第一版作为条件表达式，或者单个 def body 内的糖；按源码顺序选择第一个成立分支，必须有明确最终分支规则。备忘录中的 def 后 guard 写法也是可选表面形式，不自动支持重复同名定义。

Pattern guard 引入变量与失败路径，另行设计。模式函数参数和多条同名方程涉及分组合并、顺序、覆盖性、SCC 与隐式接口一致性，暂时晚于简单 guard。

块边界建议统一研究花括号与现有括号，不给不同特性各自添加 end。当前旧 match 仍用括号消歧；缩进敏感语法暂不推荐。

验收：未使用的顺序项仍执行一次；函数值不会误调用；输出、错误前事件与效果标签一致；多态绑定行为明示；字典依赖不被延迟隐藏；嵌套块边界与源码位置正确。

## DN-009：编辑器、诊断与工程质量

**状态：用户备忘录方向；助手建议排期；未实现编辑器接口。**

初衷：代码增长后，查类型和诊断不能一直靠 REPL 与人工阅读；当前施工日志也不适合普通语言使用者。

目的：降低真实程序编辑与排错成本，让语义结果可以被工具消费。

建议先语法高亮、括号/注释/snippets 和静态补全。同时设计结构化检查输出，保存时给诊断和定义类型，再扩展 hover。文件检查接口只是候选，不声称已有 `--json`。

不能用显示用 Pretty 文本解析错误类型；需要稳定错误类别、Span、定义/表达式结果。主检查接口还要区分分析恢复、实际执行与会话提交。

完整 LSP 与“逐字符实时分析”推迟到需要增量同步和未完成代码恢复时。TextMate 只负责词法高亮，不能自行计算推断类型。

近期性质测试聚焦替换/合一关系、独立实例化、候选搜索不修改普通类型、效果传播与失败回滚。用语言编写中等程序检验组合表达，而不是仅以孤立小例子决定新功能。

## DN-010：学习范围与采用门槛

**状态：学习方向，不构成语言排期。**

动态类型、gradual typing、子类型、显式泛型、System F、kind、higher-rank、row、GAT、handlers 可用于理解替代设计。语言间类比帮助提出问题，但不能代替当前项目的成本和语义验证。

采用前至少回答：问题是否真实且重复；现有机制能否组合解决；是否需要新类型结构/求解规则；普通推断、候选一致性和模块可见性是否可预测；用户收益是否值得长期维护。
